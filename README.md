# Hash-Table-Rebuild

# Когда окупается перестроение хеш-таблицы?

Проект для исследовательской статьи о хеш-таблицах с двойным хешированием на C++. Главный вопрос — сколько поисковых запросов должно пройти после массового удаления ключей, чтобы выигрыш от ускорения поиска покрыл время, потраченное на перестроение таблицы.

## Зачем перестраивать таблицу

При удалении ключа в его ячейке остаётся метка `DELETED`. Если поиск встречает такую метку, он продолжает проверять следующие ячейки, поскольку нужный ключ мог попасть в одну из них при коллизии. Поэтому даже после удаления половины записей поиск отсутствующего ключа может требовать нескольких проверок.

При перестроении сохранившиеся ключи переносятся в новую таблицу той же ёмкости. Метки удаления исчезают, но сам перенос занимает время. Выгода зависит от того, сколько запросов предстоит выполнить и как часто искомого ключа нет в таблице.

## План эксперимента

1. Заполнить таблицу на 80 %, затем удалить половину вставленных ключей.
2. Подготовить две копии полученной таблицы. В первой сохранить метки удаления. Вторую перестроить, измерив время переноса. Проверить, что обе таблицы содержат одинаковые ключи и имеют одинаковую ёмкость.
3. Подготовить три серии запросов с долей неуспешных поисков 10 %, 50 % и 90 %. В каждом сценарии подать обеим таблицам одни и те же запросы в одинаковом порядке.
4. Измерить время поиска. Повторить замеры на нескольких наборах ключей, чередуя порядок запуска таблиц. Отдельным прогоном подсчитать среднее число проверенных ячеек на запрос.
5. Для каждого сценария оценить порог окупаемости и проверить его на сериях запросов разной длины.

## Как оценить окупаемость

Средняя экономия на запросе равна разнице между временем поиска в таблице с метками и временем поиска после перестроения. Если экономия положительна и превышает разброс измерений, порог можно оценить по формуле:

`Число запросов до окупаемости ≈ время перестроения / средняя экономия на одном запросе`

Обе величины должны быть выражены в одинаковых единицах времени. Для проверки сравним полное время выполнения серии запросов двумя способами. В первом случае учитывается только поиск, во втором — перестроение и весь последующий поиск.

## Рабочая гипотеза

Чем выше доля запросов к отсутствующим ключам, тем раньше окупится перестроение. Итогом эксперимента станет график суммарного времени в зависимости от числа запросов. Для каждого сценария он покажет, удалось ли наблюдать точку окупаемости в исследованном диапазоне.

## Сборка и запуск

Из корня проекта:

```sh
clang++ -std=c++17 -O2 -Wall -Wextra main.cpp mod.cpp -o benchmark
./benchmark
```

Программа формирует четыре набора с фиксированным начальным значением генератора. В каждом наборе из 1013 ячеек заполняются 810, затем удаляются 405 ключей. Для промахов используются удалённые ключи. Последний столбец включает время перестроения и поиска.
